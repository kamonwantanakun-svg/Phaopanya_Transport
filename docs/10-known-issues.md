## 1. ข้อจำกัดของข้อมูลที่สกัดมา

### 1.1 กลไกเดียวกันทั้งหมด — “หัวค่าหาย หางค่าหลุด”

PDF ที่ AppSheet สร้างวาง label ของฟิลด์ **กึ่งกลางช่องของค่า** ถ้าค่ายาว (สูตร, JSON)
ตัวแยกค่าอิงบรรทัดของ label จะทำให้

- **หัวของค่าหาย** (เหลือแต่ส่วนท้ายของสูตร/JSON) และ
- **หางของค่าหลุดไปติดกับฟิลด์ถัดไป** (เช่น `Position`, `Disable automatic updates?`,
  `Is this format rule disabled?`, `read_only`, `created_by`)

→ ข้อมูล **จำนวนรายการ** ถูกต้อง 100 % (ตรวจแล้ว 8/8 ตัวเลขตรงกับหน้า 1 ของ PDF)
แต่ **เนื้อหาในบางฟิลด์** เสียรูป

## 2. ข้อสังเกตเชิงออกแบบที่ควรตรวจในแอปจริง

> ข้อสังเกตเหล่านี้ **ไม่ใช่ข้อผิดพลาดของการสกัดข้อมูล** แต่เป็นจุดที่ควรตรวจในตัวแอป
> เพราะกระทบการเงินและการทำงานจริง

### 2.1 ⭐ `ราคา` เป็น Initial value แต่มีสูตร IFS ยาวมาก

`ข้อมูลการวางบิล.ราคา` เป็น **Initial value** (คำนวณครั้งเดียวตอนสร้างแถว แก้ได้ทีหลัง)
แต่สูตรคือ `IFS` 4 เงื่อนไขที่อ้าง `เรทดีเซล`, `ระยะทางที่วิ่ง (KM)`, `ราคาตามระยะทาง`,
`ราคาจุดเพิ่ม`, `ราคาเพิ่ม` — หน้า 119

**ผลกระทบ:** ถ้าผู้ใช้แก้ `เรทดีเซล` หรือ `ระยะทางที่วิ่ง (KM)` หลังสร้างแถว
`ราคา` **จะไม่อัปเดต** ขณะที่ `ราคาตามระยะทาง` / `ราคาจุดเพิ่ม` / `ราคาเพิ่ม` / `ราคาหลังส่งสินค้า`
เป็น App formula และ **จะอัปเดต** → ตัวเลขสองชุดจะไม่ตรงกัน
และ `ราคาที่อนุมัติแล้ว = IF([สถานะการอนุมัติ] = "อนุมัติ", [ราคา], 0)` ยึดกับค่า `ราคา` ที่ผู้ใช้แก้ได้

**แนะนำ:** ย้ายเป็น App formula หรือกำหนด `Reset_If` ให้ชัดเจน
(`ราคา` มี `Reset_If = =[_THISROW_BEFORE].[ชื่องาน] <> [_THISROW].[ชื่องาน]` อยู่แล้ว — หน้า 119)

**กรณีเดียวกัน:** `รับงานคืนได้เงิน200.ราคา` เป็น Initial value ที่คำนวณจาก
`สถานะการเข้ารับสินค้า` — ถ้าผู้ใช้เปลี่ยนสถานะทีหลัง ราคาจะไม่ตาม (หน้า 245)

### 2.2 ⭐ ค่าจุดเพิ่ม “ต่างกัน 1 จุด” ระหว่างสองตาราง

| ตาราง | เงื่อนไข | หน้า |
|---|---|---:|

### 2.3 ⭐ ค่า Enum ที่สูตรเทียบ “ไม่ตรงกับชื่อที่ประกาศ”

`รับงานคืนได้เงิน200.ราคา` เทียบ `[สถานะการเข้ารับสินค้า] = "(ทำเบิก ค่ายกขึ้นชั้น)"` (มีช่องว่าง)
แต่ค่า Enum ที่ PDF หน้า 230 พิมพ์คือ `ทำเบิกค่ายกขึ้นชั้น` (ไม่มีช่องว่าง)
→ เงื่อนไขนี้ **มีแนวโน้มไม่เคยเป็นจริง** และค่า `ราคา` จะเป็นค่าว่างในกรณีนั้น
(ต้องตรวจในแอปจริงว่าชื่อที่ใช้ใน Enum คือแบบไหน)

### 2.4 ⭐ ฟอร์แมตรูล `Green_Done` เทียบค่าที่ไม่มีใน Enum

- `Green_Done` เงื่อนไข `=[ScanStatus] = "สแกนแล้ว"` (หน้า 1808)
- `สแกนรับแล้ว` เงื่อนไข `=[ScanStatus] = "สแกนรับแล้ว"` (หน้า 1809)
- ค่า Enum จริงของ `ScanStatus` (PDF หน้า 157) = `รอสแกน`, `คลังตัดสินค้า`, `สแกนรับแล้ว`

→ กฎ `Green_Done` เทียบค่าที่ไม่มีในรายการ → มีแนวโน้มไม่ทำงาน
(ข้อมูลในเอกสารไม่ยืนยันว่าค่า “สแกนแล้ว” มีจริงในแอปหรือไม่ — ให้ตรวจในแอป)

### 2.5 ⭐ ตารางที่ “มีเงินรวม” แต่ไม่มี Security filter

Security filter มีเพียง 7 ตาราง แต่ตารางที่มี **ยอดเงินรวม** ต่อไปนี้ **ไม่มี**:
`สรุปเบิกส่วนต่าง` (รวมค่าขนส่งส่วนเพิ่ม) · `FILTER` (ราคา_ได้เพิ่ม…) ·
`ปริ๊นใบวางบิล` (ราคารวม) · `PDFพนักงาน` (ราคารวม) · `ราคาในระบบก่อนส่งสินค้า` ·
`ข้อมูลงานRW` · `ข้อมูลงานRT` · `Doc_Return` · `ราคาน้ำมันดีเซล`

→ USER อ่านได้ทั้งที่ update mode เป็น `READ_ONLY` — เป็นการเปิดข้อมูลข้ามคน
ควรตรวจว่าตั้งใจให้เห็นทั้งทีมหรือไม่

### 2.8 สูตร `เรทดีเซล` มี logic ซ้อน 3 ชั้น + ใช้วันที่ 25 ของเดือนก่อน

`ข้อมูลการวางบิล.เรทดีเซล` (หน้า 136–137) เลือกราคาน้ำมันตามลำดับ:

1. `PriceOverride` ที่ `JobName` = ชื่องานของแถว (ทับราคาเฉพาะงาน)
2. `PriceOverride` ที่ `JobName` ว่าง (ทับราคาทุกงาน)
3. ถ้าไม่มีข้อ 1–2 → ราคาน้ำมันของวันที่ **25 ของเดือนก่อนหน้า** (`EOMONTH(…, -1)`)

→ ถ้าวันที่ปัจจุบันอยู่ก่อนวันที่ 25 ระบบจะย้อนไปใช้ราคาเดือนก่อน
เป็นตรรกะทางธุรกิจที่ **ควรยืนยันกับผู้ใช้** เพราะมีผลกับราคาทุกใบ

### 2.12 `USERROLE()` เขียนไม่เหมือนกัน 14 รูปแบบ

`=USERROLE() = "ADMIN"` · `=USERROLE()="ADMIN"` · `=USERROLE()= "ADMIN"` · `=USERROLE( )="ADMIN"` ·
`=USERROLE()="ADMIN "` · `=OR( USERROLE() = "ADMIN" , …)` · `=IF(USERROLE() = "ADMIN", …)` …
รวมถึง `USERROLE() = ADMIN` (ไม่มีเครื่องหมายคำพูด) และ `USERROLE() = "Admin"` (ตัวพิมพ์ต่าง)

→ **ไม่ทำให้แอปพัง** แต่ทำให้ค้นหา/แก้ไขยาก และเสี่ยงถ้ามีการเปลี่ยนชื่อในอนาคต
ควรปรับให้เป็นรูปแบบเดียวทั้งแอป

### 3.5 กฎที่ควรยึดเมื่อวิเคราะห์

1. อย่าแก้ไฟล์ใน `data/` โดยไม่ได้ยืนยันกับ PDF ก่อน
